# Outbox operation and retry scheduling

`GET /api/notification/outbox` drains only persisted pending work. It requires `Authorization: Bearer <CRON_SECRET>`, fails closed without configuration and returns sent/pending/failed metrics only. It does not accept recipients, templates, IDs or payloads. The worker claims at most 50 jobs, uses a 45-second work budget and sequential provider calls, with a 60-second route duration. Missing email configuration retains pending work without consuming attempts. Check deployment duration and connection budgets before release.

The digest remains scheduled at 10:00 UTC in `vercel.json`. Daily notification identity uses the Europe/Madrid date, including DST and payday month-end clamping. A daily call alone cannot guarantee automatic retries inside the 23-hour idempotency cutoff. Configure the worker at least hourly (five minutes recommended) and monitor failures/backlog age before enabling production email.

[Vercel's current cron limits](https://vercel.com/docs/cron-jobs/usage-and-pricing) allow only once-daily cron expressions on Hobby; more frequent schedules fail deployment. Pro/Enterprise allow minute intervals. `vercel.pro.example.json` provides the proposed five-minute worker schedule alongside the digest. It is an example, not the active manifest. After confirming a compatible plan, copy/review its cron entries in `vercel.json`. On Hobby, configure an explicitly approved external scheduler to call the protected worker; none has been provisioned by this remediation.

Keep CRON_SECRET server-only and in scheduler secret storage. Do not put it in URLs, browser code or logs. Verify the scheduler's actual Authorization header on the deployed route. Confirm RESEND_KEY and sender-domain configuration separately. Alert on failed jobs, old pending work, exhausted retry windows and scheduler failures. Metrics count the selected batch, not the entire queue; inspect persisted outbox state privately for total backlog.

Resend keys remain stable for the notification ID. Retry count is capped at five, with exponential retry timing and a 23-hour cutoff from first attempt. An expired uncertain job is marked failed and must be reconciled against the provider before any manual action. Never replay it under a fresh key without resolving whether delivery occurred. A live provider timeout/response and scheduler execution remain deployment checks; synthetic fixtures do not send real emails.
