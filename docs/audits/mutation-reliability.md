# Mutation and delivery guarantees

Loan/subscription creation and editing now commit the Contract graph, invitation accounting, notifications and rendered email snapshots in one serializable transaction. Rendering/enqueue failure rolls everything back. Share responses use a conditional pending→accepted/rejected update in the same transaction as notification/outbox work; identical retries return unchanged, and a conflicting answer is rejected. Serialization conflicts return HTTP 409 for refresh/retry; browser writes are never retried automatically.

An InvitationEvent ledger enforces at most 20 new recipients per owner in a sliding hour. Concurrent producers lock the owner's row and serialize the transaction. Existing recipients in an edit incur no charge. Deleting a share/contract does not delete attempts. Migration seeds events from retained shares created in the previous hour; earlier deletions cannot be reconstructed. Cron prunes events older than one day. This limiter is a concurrency-safe abuse bound, not an account-wide notification preference system.

Provider delivery begins after commit and targets only the new notification IDs. Failure leaves committed durable work and does not turn a successful financial mutation into a misleading HTTP failure. Daily digests enqueue without per-user delivery, then use one bounded worker pass. Missing RESEND_KEY leaves jobs pending without claiming them. Claims compare attempt count and retry time to prevent stale workers from bypassing backoff. Provider timeout uses remaining worker budget.

Loan edits now persist the validated payday. Carryover records without a LINK can be edited safely. Subscription edits target the single open period, preserving closed history; paused subscriptions must be resumed before billing edits. The UI disables billing edits while paused and hides financial mutation controls from recipients. Server ownership checks remain authoritative and precede mutation input validation.

Verified locally: 127 unit tests, seven real database transaction/delivery/quota tests, and eleven browser/API checks. Coverage includes concurrent invitation bursts, rollback of domain + outbox + quota on render failure, duplicate accepted responses, read-only recipient detail, active/closed period separation, actual pause/resume without reload, deletion-resistant limits, and authenticated repeated cron calls. Synthetic emails never leave the test environment. The production migration runner also applies the InvitationEvent migration in its backup/restore fixture.

The once-daily digest schedule alone is insufficient for prompt retries within the provider's 23-hour retry cutoff. Frequent worker scheduling must be configured for the deployment's actual hosting plan. This remains a release requirement until the plan/scheduler is confirmed; no external scheduler or paid plan has been provisioned.

New OAuth user creation and its welcome snapshot also share a transaction through the NextAuth adapter's createUser implementation. Rendering/enqueue failure rolls back the new user, so it cannot leave an unlinked account that blocks a later OAuth attempt. The post-create event only attempts durable delivery. Two additional real-database tests verify commit and rollback; the database suite now has nine tests. Real-session browser checks pass, while a real Google OAuth redirect/callback remains an external release check.
